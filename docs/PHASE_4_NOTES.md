# Phase 4 Notes

**Date:** May 2026
**Ship criterion (PRD §10):** "When I view a company, I have enough signal to decide whether to escalate it to A-tier without further research."
**Status:** Met. Every company detail page renders a numeric quality score plus the per-factor breakdown that produced it (funding recency, github activity, blog cadence, hiring volume stability, comp transparency, recent layoffs, ghost density, no-eng-presence penalty), a 90-day hiring volume chart, a timeline carrying funding / boomerang / layoff / ghost / yc-status Events, and an explicit graveyard banner when demoted. No external tab needed to make the call.

---

## What shipped

- **Step 1 — signal enrichment columns.** `companies` gains `funding_stage`, `funding_last_raised_at`, `funding_last_amount_usd`, `github_org`, `eng_blog_rss_url`, `is_active` (default true), `ats_status` (default `ok`), `ats_consecutive_404s`. Partial index `companies_tenant_active_idx ON companies(tenant_id) WHERE is_active = true` makes default queries cheap when the graveyard fills up. Second partial index on `ats_status <> 'ok'` for the redetection sweep. `aggregator_listings` gains `role_hash` (char 64) + `requisition_id` + two supporting indexes — the substrate for boomerang and ghost detection.
- **Step 2 — `company_snapshots` substrate + `signals:snapshot:daily` writer.** One row per `(tenant, company, snapshot_date)`. Columns capture today's `open_role_count`, `listings_count`, `tier`, `status`, plus nullable `github_score`, `blog_posts_90d`, `has_recent_layoff_event`, `quality_score`, and a `breakdown` jsonb. Other signal jobs (github, blog, layoffs, quality) update the same row in place later in the day; this command's job is just making sure today's row exists with the always-knowable fields populated. Scheduled at 04:00 UTC ahead of every downstream job.
- **Step 3 — company graveyard.** `company_graveyard_reasons` is append-only, one row per demote; `restored_at` + `restored_by_user_id` nullable so a restore stamps the same row. `POST /companies/{id}/graveyard` flips `status='graveyard'` + `is_active=false`, writes the reason row with preset-tag multi-select (`wrong_stack`, `bad_culture_signal`, `comp_too_low`, `geo_restrictive`, `layoffs`, `not_hiring_anymore`, `lost_interest`), and emits a `graveyarded` Event. `POST /companies/{id}/restore` reverses (status `researching`, tier C if previously `graveyard`, `is_active=true`) and emits a `restored` Event. `/companies` exclues `is_active=false` by default; `?graveyard=1` flips to graveyard-only so the same controller serves both views. Show page renders a red banner with the active reason + tags whenever a company is graveyarded.
- **Step 4 — hiring volume trend charts.** Recharts wrapped in `HiringTrendChart` (component-level empty state for fresh installs). Company show page renders the 90-day chart in the Overview tab; `/insights/hiring` renders a global A-tier aggregation (per-day `SUM(open_role_count + listings_count)` from `company_snapshots`) plus per-company sparklines. `pnpm add recharts` was the only new dependency.
- **Step 5 — `role_hash` + boomerang detection.** `RoleHasher::hash(companyKey, roleKey, locationBucket)` is sha256 over the lowercased concatenation, with `∅` sentinels for missing slots so partial keys don't collide. `AggregatorListingPersister` populates `role_hash` inline on insert and, immediately after, looks for prior listings sharing the hash with a `fetched_at` gap ≥ 14 days. On match → `boomerang` Event on the matched company carrying the gap and previous `fetched_at`. `signals:listings:rehash` is the one-shot backfill: it fills `role_hash` on existing rows (chunked 500, ~700/sec) and synthesizes historical boomerang Events de-duplicated by listing id embedded in the Event body. Hashes off `aggregator_listings` for now because `roles` is empty — when the canonical roles pipeline gets wired, the same hash flows up without code changes here.
- **Step 6 — Funding: manual entry + yc-oss diff.** `POST /companies/{id}/funding` (AddFundingController + AddFundingRequest) updates the `funding_stage` / `funding_last_amount_usd` / `funding_last_raised_at` scalars **only when the new round is at least as recent as the stored one** — stale historical entries don't downgrade the company's "most recent" view, but they still record their own Event. `signals:funding:yc-oss` (YcOssClient) fetches `https://yc-oss.github.io/api/companies/all.json` once, indexes by `CompanyKeyNormalizer`-normalized name, and emits a `funding` Event whenever a tracked company's `status` differs from the last yc-oss-source Event recorded for it. Body carries `{source: 'yc_oss', yc_status, previous_status, batch, team_size, url}`. Static GitHub Pages → effectively unlimited rate.
- **Step 7 — Google News funding scan (review queue).** `funding_candidates(tenant, company, source='google_news', external_id, title, url, published_at, matched_keywords[], status, fetched_at)` keyed unique on `(tenant, company, source, external_id)`. `GoogleNewsClient::search()` hits `https://news.google.com/rss/search?q="{company}" raised OR Series OR funding`, parses via `SimpleXMLElement`, drops items whose title doesn't contain at least one PRESET_KEYWORD (`raised`, `Series A–E`, `funding round`, `closes round`) so off-topic matches don't pollute the queue. `signals:funding:news` upserts candidates idempotently. `/insights/funding-candidates` lists `new` candidates; one-click confirm emits a `funding` Event with `source: 'google_news'` and flips the candidate to `confirmed`; dismiss flips to `dismissed`. **Nothing here auto-updates Company scalars** — Google News false-positives are too common (company-name collisions especially).
- **Step 8 — Engineering blog RSS monitor.** `company_blog_posts` table, unique on `(tenant, company, external_id)`. `BlogFeedFetcher` parses both RSS 2.0 and Atom 1.0 via `SimpleXMLElement` — no `simplepie/simplepie` or Feed-IO; the platform's RSS surface is small enough that the stdlib parser is fine and one fewer dependency. 10s HTTP timeout. `signals:blog:poll` iterates companies with non-null `eng_blog_rss_url`, upserts posts, and emits `blog_post` Events for truly-new rows. Failures are isolated per-company (one dead feed doesn't abort the sweep) and logged at WARNING via the injected LoggerInterface. Daily at 05:00 UTC.
- **Step 9 — GitHub org poller.** `GithubOrgScorer::score(org)` returns `['score', 'public_repos', 'pushed_repos_90d', 'new_repos_90d', 'fetched_at']`. Composite formula (documented in service docblock): `base = min(40, log10(max(1, public_repos)) * 20)` + `activity = min(40, pushed_repos_90d * 5)` + `innovation = min(20, new_repos_90d * 4)`. Authed via `GITHUB_TOKEN` env var (5000 req/h budget vs 60/h anonymous). `signals:github:poll` upserts onto today's `company_snapshots.github_score`. 100 ms sleep between orgs to stay polite even within budget; per-org 404 / 403 / timeout isolated, never aborts the sweep. Weekly Monday 04:30 UTC.
- **Step 10 — Layoffs cross-reference.** `LayoffsRecord` DTO + `LayoffsCsvParser` (order-independent header lookup, robust to `%` vs fraction representations and malformed dates) + `LayoffsSync` (tenant-scoped normalized-key → company_id map, sha1(company|date|source) signature embedded in Event body for idempotent dedupe). `signals:layoffs:sync --source=local --path=...` reads from a staged CSV (scheduled to look at `storage/app/signals/layoffs.csv`). `--source=kaggle` returns FAILURE with a clear "set --source=local" message — auto-Kaggle download is a follow-up. **Layoff Events never flip `is_active`** — a layoff is a signal, not a death sentence; graveyarding stays manual.
- **Step 11 — ATS-switch detection.** `ScrapeOrchestrator::recordAtsHealth()` runs on every exit path of `runForCompany`. Each ATS scraper (Greenhouse / Lever / Ashby) short-circuits on `status >= 400` and records `errors[].context.http_status` so the orchestrator can tell a 404 apart from other transport failures. 404 → `ats_consecutive_404s++`; completed / not_modified → reset to 0; threshold of **7** → `ats_status = 'needs_redetection'`. `signals:ats:redetect` runs hourly, iterates flagged companies, calls `AtsRedetector` (which re-runs `AtsDetector` against the careers URL + every URL found in the page body). Success → update `ats_type` + `ats_slug`, reset counters, emit `ats_redetected` Event. Failure → bump `ats_redetect_attempts`; at **3** failed attempts the company flips to `redetect_failed` and surfaces on `/admin/runs` (closest existing admin surface — there's no `/admin/sources` yet).
- **Step 12 — Ghost-job detection.** Four OR'd heuristics, every flag carries the reason codes that fired. `GhostJobDetector::detect(listing)` returns `list<string>`:
  - `posted_age_gt_60d` — `posted_at` older than 60 days, listing still NEW/KEPT/LINKED.
  - `requisition_reposted` — `requisition_id` appears in 2+ `new_role` Events for the matched company.
  - `layoffs_within_30d` — matched company has a `layoff` Event in the last 30 days.
  - `aggregator_breadth_3` — same `role_hash` appears across ≥ 3 distinct aggregator sources AND no open Role exists on the company's own ATS.
  Thresholds in `config/signals.php` (`ghost.posted_age_days_threshold`, `requisition_reappearance_threshold`, `layoff_proximity_days`, `aggregator_diversity_threshold`). `signals:ghost:scan` runs daily 05:30, persists `ghost_flag` + `ghost_reasons` jsonb on `aggregator_listings`, and emits a `ghost_detected` Event the **first** time a listing tips into flagged status (subsequent passes are silent so the quality score doesn't double-count). DISMISSED / AUTO_DISMISSED / DUPLICATE listings are skipped.
- **Step 13 — Compensation aggregation insights.** `/insights/comp` renders three tables (role family, geography, per-company) of P25 / median / P75 USD comp derived from `(parsed_comp_min_usd + parsed_comp_max_usd) / 2`. Postgres `PERCENTILE_CONT(0.x) WITHIN GROUP`. Role family inferred via regex over `parsed_role_title` (level prefix + discipline keyword); geography bucketed from `parsed_remote_type` + `location_bucket` into US / EU / Global Remote / Other. Per-company aggregation filters to listings with ≥ 3 samples and limits to top 50 by sample count. Status filter excludes dismissed / duplicate / auto_dismissed.
- **Step 14 — Company quality score.** `QualityScorer::compute(Company)` returns `['score' => int, 'breakdown' => array<string, ['weight', 'contribution', 'value']>]`. Baseline 75; positive contributors (`funding_recency` 15, `github_activity` 15, `blog_cadence` 10, `hiring_volume_stability` 20, `comp_transparency` 10) plus three penalties (`layoff_penalty` −20, `ghost_density_penalty` −15, `no_eng_presence_penalty` −10). Final score clamped to `[1, 100]`. Weights live in `config/signals.php → quality_score.*`. `signals:quality:recompute` runs daily 05:45 UTC, after every input job. Upserts onto today's `company_snapshots` row (`quality_score`, `breakdown`, `has_recent_layoff_event`).
- **Step 15 — Quality breakdown UI.** `QualityCard` on the company show page renders the numeric score (color-toned: green ≥80, amber ≥60, red below) plus a per-factor table with weight and signed contribution. Footer paragraph names the math ("score starts at the baseline and is adjusted by each factor; positive factors max at their weight; penalties subtract up to their weight"). Empty state when no `quality_score` has been written yet — the recompute job is what creates it.
- **Step 16 — Unlock Phase 3 placeholder filters.** Two of the five Phase 3 placeholder dimensions now narrow live: `stage` (multi-select from distinct `funding_stage` values in the tenant) and `recently_funded` (single-toggle chip for `funding_last_raised_at >= now() - 18 months`). The other three (`size`, `remote_policy`, `primary_stack`) stay visually present but disabled with explanatory tooltips — `size` has no underlying column (the project doesn't track headcount), and `remote_policy` / `primary_stack` live at the listing level, not the company level. Saved views still round-trip the deferred keys.

## Deviations from PRD (and from the kickoff plan)

- **Step 6 yc-oss tracks `status`, not `funding_stage`.** yc-oss doesn't carry funding amounts — its `status` field (Active / Acquired / Inactive / Public) is the closest funding-adjacent signal. The "funding" Event records the status transition, not a round. Manual entry remains the path for actual round + amount data.
- **Step 7 candidates are user-gated, never auto-applied.** PRD §6.3.5 already specified this, but worth restating: Google News false-positives are common (company-name collisions, off-topic earnings-call mentions). The `funding_candidates.status` lifecycle (`new` → `confirmed` | `dismissed`) is the human gate.
- **Step 8 uses stdlib `SimpleXMLElement`, not SimplePie / Feed-IO.** The PRD floated those libraries; stdlib does the job for the RSS + Atom shapes we see in practice and avoids the extra dependency.
- **Step 10's Kaggle auto-download is deferred.** The Kaggle API requires auth + dataset-version handling that wasn't worth implementing inline. `--source=local --path=...` is the path; the scheduled run reads from `storage/app/signals/layoffs.csv` which the operator stages manually. TrueUp fallback (PRD §4.2) is similarly deferred — same `--source=local` pattern when needed.
- **Step 11 surfaces redetect failures on `/admin/runs`, not `/admin/sources`.** `/admin/sources` doesn't exist as an Inertia surface; `/admin/runs` is the existing scrape-health page. When a dedicated sources admin lands, the banner moves there.
- **Step 12's `aggregator_breadth_3` heuristic compares against the `roles` table.** Currently empty in the live DB, so the heuristic effectively reduces to "same role_hash on 3+ aggregator sources" until the canonical roles pipeline is wired. That's still the right test — when roles populate, the heuristic gains the "missing from company's own ATS" leg without code changes.
- **Step 13 role-family inference is regex-based, not enum-driven.** Free-form `parsed_role_title` doesn't map cleanly to a fixed taxonomy; the regex picks up level prefix + discipline keyword and falls back to `Other`. Good enough for a first pass; replaceable when a structured role-family parser lands.
- **Step 14's `hiring_volume_stability` requires ≥ 10 days of snapshot history to be meaningful.** Fresh installs (1-2 days of data) will see a near-zero `oldAvg`, which makes the change ratio either 0 (matched) or undefined-treated-as-0. The math is correct but the dimension is weak until the table fills up. Quality score in the meantime leans on funding / github / blog / comp.
- **Step 16 only wired `stage` and `recently_funded`.** `size`, `remote_policy`, `primary_stack` need: a company-level size column (doesn't exist), aggregation of `aggregator_listings.parsed_remote_type` into a company-level summary (needs a rollup job), and aggregation of `stack_tags` similarly. All three are Phase 5+ scope.
- **Database state: rollback dance during step 12.** The ghost migration was first generated empty (the artisan stub) and ran successfully as a no-op before I wrote real content into the file. Recovery: deleted the migration row from the `migrations` table by hand, re-ran. The five subagents that landed in parallel meant the working directory had work-in-flight from multiple sources; future parallel-agent work should either use isolated worktrees or block agents from running migrations entirely.

## Decisions worth carrying into Phase 5+

- **The quality score must remain explainable.** Every factor's `weight`, `contribution`, and raw `value` is stored in the `breakdown` jsonb so the UI can render the math line-by-line. New factors should follow the same shape. If a factor needs more than a single numeric contribution, refactor the shape rather than collapsing it.
- **Weights live in config, not the DB.** `config/signals.php` is the single source of truth for ghost thresholds and quality-score weights. If a value starts needing per-tenant tuning, promote it to a row in `settings` — but only once. Resist the urge to make every knob tunable; the rest of the platform is single-tenant.
- **Snapshots are the substrate. Other jobs update in place.** `signals:snapshot:daily` is the only writer that *creates* a `company_snapshots` row for today. Github / blog / quality jobs all `upsert` onto the same `(tenant, company, snapshot_date)` key, never insert new rows. New signals should follow the same pattern.
- **Aggregator listings carry the role-level signals until canonical roles ship.** `role_hash`, `requisition_id`, `ghost_flag`, `ghost_reasons` all live on `aggregator_listings`. When the `roles` table gets wired, these flow up without code changes — the column names already match what a role-level taxonomy would use.
- **Graveyard is read-mostly. Don't add side effects to the demote path.** The reason row is append-only; restoration stamps the same row. Auto-dismiss-driven graveyarding (PRD §6.2.8, "3+ dismissals") is *not* implemented yet — when it lands, it goes through the same controller, not a side channel.
- **The Event timeline is the audit log.** Every signal that matters to the user surfaces as an Event with a structured body (JSON). Don't write side-channel logs that the UI doesn't read. If a job decides something is worth surfacing, it's worth an Event.
- **Parallel-agent work should use isolated worktrees.** This phase ran five subagents in parallel via the main working directory. It worked, but caused interleaved edits to shared files (route table, enum, scheduler) and one migration-table-state recovery. Next phase: `isolation: "worktree"` for any agent that creates schema or touches shared files, and merge the worktrees back into main serially.
